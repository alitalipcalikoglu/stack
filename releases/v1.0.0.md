# Stack v1.0.0

First tagged release of the 15-repo `atc-web` platform: `stack` (orchestration), `service-core`
(shared runtime library, pinned at `v1.11.1`), and 13 independently deployable services — `gateway`,
`notify`, `auth`, `media`, `console`, `audit`, `shortlink`, `flags`, `scheduler`, `webhook-out`,
`search`, `ratelimit`, `geo`.

None of these 14 repos (every one except `service-core`) had a prior tagged release — `1.0.0` is
each one's first, not a version bump past prior history that never existed. `service-core` keeps its
own already-established tag-per-release history; `v1.11.1` is not re-tagged here, only referenced as
this release's baseline dependency.

## What this release covers

- **Shared runtime (`service-core` v1.11.1)**: request lifecycle, structured logging, SQLite access
  with migration tracking, HTTP client/audit-forwarding primitives, and centralized W3C
  `traceparent` trace-context consumption and trusted internal propagation, consumed by all 12
  backend services and `console`.
- **Migrations**: every service's schema migrates automatically on startup from any real prior
  version; a concurrent split-worker first start against a pending migration is race-safe
  (SQLite `BEGIN IMMEDIATE` arbitration, proven with real, separate OS processes).
- **Split workers**: `notify`, `scheduler`, `webhook-out` support an API + worker split topology
  (`stack up --split-workers`), generating a per-service split PM2 ecosystem file from each
  service's own combined one.
- **Backup/restore**: `stack backup` snapshots every service's database (via `VACUUM INTO`, safe
  against a live process) plus the extra paths a database alone can't reconstruct (media's object
  store, auth's JWT keys, audit's optional anchor key, gateway's `routes.json`, console's
  `services.json`). `stack restore` validates everything before touching anything, applies as one
  atomic prepare/apply pass per call with full rollback on failure, and — as of this release —
  correctly clears a live database's `-wal`/`-shm` sidecar files as part of that same atomic unit, so
  a service that was not cleanly closed before a restore never has a stale, un-checkpointed write
  silently reappear after restore.
- **Media storage**: content-addressed blob storage with deduplication, ticketed uploads, soft
  delete with a grace-period trash/quarantine reconciliation pass.
- **Gateway**: route-table-driven reverse proxy with JWT verification, rate-limit policy delegation,
  upstream health tracking and circuit breaking, geo header injection, and trace propagation to
  matched upstreams.
- **Audit**: hash-chained event log with optional Ed25519 anchor signing and chain verification,
  consumed by every other service for write/security event forwarding.
- **API/schema compatibility**: every service exposes `GET /v1/info` (service, version, apiVersion,
  schemaVersion, serviceCore, capabilities) through a single shared implementation; `stack status
  --matrix` reads it live across the whole running platform — see `releases/v1.0.0.json` for a
  point-in-time snapshot (a generated convenience, not the source of truth; the live endpoints and
  each repo's own git tag remain that).
- **Production validation**: every claim above was proven against real, running processes and real
  disposable environments, not mocked — see "Evidence" below.

## Known limitations

- **PM2 supervision itself was not exercised in this release's own validation environment** — PM2 is
  not installed there. What *was* proven for real: all 13 services' `ecosystem.config.cjs` (and the
  3 split-capable services' generated split variant) parse and have the correct shape PM2 would load;
  every real production entrypoint starts, serves, and shuts down gracefully under a direct child-
  process harness equivalent to what PM2 itself would run. Actual `pm2 start`/`pm2 stop` process
  supervision should be exercised once in a real environment with PM2 installed before depending on
  it operationally.
- **No GitHub Actions/CI pipeline** — a deliberate project decision (see `stack/docs/RELEASE_AUDIT.md`
  §16), not an oversight. Release validation is local: the exact commands in
  `stack/docs/RELEASE_AUDIT.md` §6, run before every release.
- **`AuditClient`/`GeoClient` do not propagate trace context** — both batch or cache across many
  original requests, so there is no single request to attribute a trace to; a deliberate, documented
  scoping decision, not a gap.
- **No distributed multi-instance guarantees beyond what's documented per-service** — `gateway` is
  the only service explicitly designed to run more than one instance behind a load balancer (its
  circuit-breaker state is per-instance, by design); every other service's own `docs/READINESS.md`
  states its own scaling class.
- **Backup encryption at rest is an operator responsibility** — a snapshot directory contains real
  key material (JWT signing keys, the optional audit anchor key) in plaintext on disk; protecting
  that directory (filesystem permissions, disk encryption, off-host storage) is not something `stack
  backup` does for you.

## Evidence

Full detail in `stack/docs/RELEASE_AUDIT.md` and `stack/docs/RELEASE_PLAN.md`. Summary of what was
run and passed, against this exact release's validated source state:

- 15/15 repos: `npm ci && npm test && npm run typecheck` green (`console` also `npm run build`;
  `stack` plain suite 40/40).
- `stack` `STACK_INTEGRATION=1`: 70/70 (migration race, migration E2E, audit anchor continuity,
  cross-service trace propagation, and more — real, separate-process tests throughout).
- All 13 deployable services: real production-entrypoint startup smoke (concurrent, real
  `stack.setup()`-generated wiring) — 13/13 `/ready` + `/v1/info`, graceful shutdown, zero
  source-tree mutation, ports released.
- Real live `stack status --matrix` run against all 13 running services.
- Real split-mode (separate API + worker OS processes) job flows for `notify`, `scheduler`,
  `webhook-out`.
- 7 services' `package-lock.json` verified installable and green in real `node:22-alpine`
  (`--platform linux/amd64`) — the same runtime family every service's own `Dockerfile` deploys with.
- Real system-level upgrade drills (old-schema fixture → real process → real migration → `/ready` →
  data preserved → real second start proving idempotency) for 6 representative services: `notify`,
  `console`, `webhook-out`, `auth`, `audit`, `media`, `scheduler`.
- A real, coherent multi-service backup → mutate → restore → restart drill across `media`, `audit`,
  `notify`, `scheduler`, `webhook-out` together, one shared backup generation, proving the WAL/SHM
  restore fix under genuine (not manufactured) SQLite WAL activity.
